# M0 验证手册

目标：1~2 天内把 5 个会**改写架构**的问号变成确定答案。在做完之前不要写产品功能。

## 安装

```bash
cd RuyueAlarm
./gradlew assembleDebug
adb install -r app/build/outputs/apk/debug/app-debug.apk
```

装完第一次打开，先点第 6 项「HyperOS 设置引导」，把那些开关都打开 —— **否则后面全部结论都不可信**。

## ① WiFi SSID 权限验证

**要回答的问题**：能不能稳定读到 WiFi 的 SSID，以及**到底需要哪些权限**？

> **第一轮实测（2026-09，小米 15 Ultra / HyperOS，v0.1.0-m0）**
> `NEARBY_WIFI_DEVICES` 与 `ACCESS_FINE_LOCATION` **都已授予**，SSID 依然是 `<unknown ssid>`。
> 原因：manifest 给 `NEARBY_WIFI_DEVICES` 加了 `neverForLocation` 标记 —— 它等于声明
> 「本应用不通过 WiFi 推断位置」，系统便把 SSID/BSSID 这类位置性信息一并抹掉。
> **v0.1.1-m0 已移除该标记**，并同时显示两条读取路径 + 系统定位总开关，用来一次分清剩下几种可能。

> **第二轮实测（2026-09，v0.1.1-m0，已移除 neverForLocation）**
> 重装后 `ACCESS_FINE_LOCATION` 变成**未授予**（HyperOS 在权限声明变化后重装似乎会重置运行时权限），
> 于是这一轮实际测的是「只有 `NEARBY_WIFI_DEVICES`」：**SSID 仍被抹除**。
> → 说明 `NEARBY_WIFI_DEVICES` 单独**不足以**读 SSID，位置权限是必需的。
>
> **第三轮实测（2026-09，v0.1.1-m0，三权限齐全）→ ✅ 结案**
> 读到真实 SSID `plqrd_5GHz`、BSSID `9c:21:6a:f8:83:94`。
> 但**主路径 `NetworkCapabilities` 仍返回抹除值，只有备用路径 `WifiManager` 读到真名** ——
> 这是本轮最重要的发现：M1 必须走 `WifiManager.connectionInfo`。
>
> **最终规则**：`NEARBY_WIFI_DEVICES` + `ACCESS_FINE_LOCATION`（后台读还要
> `ACCESS_BACKGROUND_LOCATION`），且**不能**声明 `neverForLocation`；读取必须用
> `WifiManager` 那条路。

步骤（v0.1.1-m0 起）：
1. 先确认 App 版本是 `0.1.1-m0`（① 页顶部的「App 版本」那一行）
2. 连上目标 WiFi，并确保系统「定位」总开关是**打开**的
3. 点「读取一次」→ 看「诊断」那一行给出的结论
4. 若提示缺位置权限，点「**申请精确位置并读取**」再读一次

| 结果 | 结论 |
|---|---|
| 读到真实 SSID | 记下「来源」是主路径还是备用路径；M1 需声明 NEARBY_WIFI_DEVICES + ACCESS_FINE_LOCATION |
| 只有系统定位关着时才读不到 | 正式版要在引导页提示用户打开系统定位 |
| 权限齐全 + 定位开着仍读不到 | 把 ① 页截图发我，转向排查 ROM 侧限制 |

**记录**：`✅ 2026-09-30 读到 plqrd_5GHz（来源：备用路径 WifiManager）；主路径仍脱敏`

## ② 前台服务保活

**要回答的问题**：HyperOS 会不会在锁屏一段时间后把哨兵服务杀掉？

步骤：
1. 进「② 前台服务保活」→ 点**启动哨兵**（状态变成「运行中」）
2. 按电源键锁屏，正常用手机 **8 小时以上**（别去点「强行停止」）
3. 回来进「全部日志」，看时间线：
   - 心跳每 5 分钟一条、连续不断 → ✅ 保活有效
   - 心跳断档 / 出现 `SERVICE_STOP` 之后没有 `SERVICE_START` → ❌ 被杀了
4. 再**重启手机**，看服务是否自动变回「运行中」（验证开机自启动）

| 现象 | 结论 |
|---|---|
| 心跳连续 + 重启自动恢复 | 保活策略可用，M1 直接用 |
| 心跳断档 | 按顺序排查：HyperOS 自启动 → 省电策略无限制 → 通知权限 → Doze 白名单 |
| 重启没恢复 | `BOOT_COMPLETED` 没收到（看日志有没有 `BOOT`），或 Android 15 拒绝了 FGS 启动 |

**记录**：`8 小时后心跳：连续 / 断档____  重启后：自动恢复 / 没恢复____  日期：________`

## ③ 全屏闹钟

**要回答的问题**：锁屏状态下提醒能不能全屏弹出并响铃？

步骤：
1. 进「③ 全屏闹钟」，确认「可使用全屏意图」是**可以**
2. 点**「1 分钟后提醒」**→ 立刻按电源键锁屏 → 等
3. 看结果：
   - 屏幕自动亮起 + 全屏响铃页 → ✅
   - 只有横幅通知 → 全屏意图被拒（去页面上「打开全屏通知系统开关」）
   - 完全没动静 → 看日志有没有 `ALARM_FIRED`
4. 故意关掉 HyperOS 的「后台弹出界面」再测一次，确认降级路径（横幅通知）也能提醒到你

判读：
| 日志 | 界面 | 结论 |
|---|---|---|
| 有 `ALARM_FIRED` | 全屏响了 | ✅ 完美 |
| 有 `ALARM_FIRED` | 只有横幅 | 全屏意图/后台弹出界面问题 |
| 没有 `ALARM_FIRED` | 没反应 | 闹钟本身没触发 → 查精确闹钟权限 / 保活 |

**记录**：`锁屏全屏：可以 / 只横幅 / 没反应____  日期：________`

## ④ 高德围栏（需先申请 key）

**要回答的问题**：围栏触发延迟多大？息屏还能不能触发？一天耗多少电？

启用步骤（详见「④ 高德围栏」页面）：
1. 高德开放平台申请 Android 定位 SDK key，绑定包名 `com.ruyue.alarm` + **debug 签名 SHA1**
   ```
   keytool -list -v -keystore %USERPROFILE%\.android\debug.keystore -alias androiddebugkey -storepass android -keypass android
   ```
2. 把 key 填进 `RuyueAlarm/gradle.properties` 的 `AMAP_KEY=`
3. 打开 `app/build.gradle` 里 `com.amap.api:location` 的注释（版本号换高德当前推荐值）

要测的：
- 圆形围栏最小可用半径（一般 200 米量级）
- 进/出各走一遍，记录**从进入到响铃的实际延迟**
- 息屏 + 锁屏状态下能否触发
- 跑一天看 HyperOS 耗电排行里的占比

**记录**：`半径____米  延迟____秒  息屏能否触发____  耗电____%  日期：________`

## ⑤ 连断统计与去抖

**要回答的问题**：这条提醒的「到达」判定要多保守？

前提：② 的哨兵已经开了一整天。

1. 进「⑤ 连断统计与去抖」，看近 24 小时：WiFi 连上几次、断开几次、按 SSID 分组
2. 定两个参数：
   - **连接确认时间**：连断频繁（≥10 次/天）给 30 秒以上，否则 10~15 秒
   - **触发冷却**：建议默认「同一条提醒每天只触发一次」
3. 顺便看「心跳最大间隔」：>600 秒说明那段时间服务被挂起或被杀了（回到第 ② 项）

**记录**：`一天连上____次  确认时间定为____秒  冷却定为____  日期：________`

## 结果汇总

实时结论统一记在文末的「M0 实测记录」表，避免两份表不同步。

## ⚠️ 一个必须在 M3 复核的前提

M0 用的是 **compileSdk/targetSdk 34**（与同机已验证的 BlinkNote 一致，先保证能编能跑）。
代价：Android 15/16 上部分限制会以「兼容模式」运行。

以下三项的 M0 结论**在上架前升到 targetSdk 35/36 之后要再验一次**：

1. 前台服务类型（`specialUse` 在 Android 15 的启动限制）
2. 全屏意图（Android 14+ 的应用类型限制）
3. 从 `BOOT_COMPLETED` 启动前台服务（Android 15 限制了部分类型）

### ② 暴露的两个缺口（均已在 v0.1.2-m0 修掉，等复测确认）

**缺口 1：没有自愈机制（致命）→ 已修**

现象：10-01 00:28 哨兵被杀后，直到 10-08 用户手动打开 App 才有动静，中间 **7 天一条日志都没有**
（期间没重启过手机，所以开机自启那条路也没机会生效）。对「到达提醒」产品，服务悄悄死掉 = 功能失效。

修法：新增 `sentinel/SentinelWatchdog.kt` —— 用 `AlarmManager` 每 15 分钟触发一次
`WatchdogReceiver`，读数据库里**最后一条心跳**判断服务是否还活着（不能用内存状态，
进程被杀后就没了），死了就拉起来并往日志里写一条 `NOTE`。

为什么不用 WorkManager：Android 12+ 禁止后台启动前台服务，**「精确闹钟触发的广播」是官方豁免之一**，
WorkManager 的任务没有这个豁免，会抛 `ForegroundServiceStartNotAllowedException`。
没拿到精确闹钟授权时退化成不精确闹钟，失败会记 `ERROR` 而不是静默。

> 因此 ② 页新增一行「看门狗精确闹钟」。
> **注意**：v0.1.2 曾让用户去系统「闹钟和提醒」列表手动授权 —— 实测发现
> **Android 14 起该列表不一定列出本应用，用户根本无处授权**。v0.1.3 改为声明
> `USE_EXACT_ALARM`（Android 13+ 的普通权限，安装即自动授予），这个问题不再存在。
> 同时补了兜底：万一自动拉起仍被系统拒绝，会发一条高优先级通知，用户点一下即可恢复。

**缺口 2：心跳日志无法回答「后台能不能读 SSID」→ 已修**

现象：`WIFI_CONNECT` / `WIFI_DISCONNECT` 的详情取自**回调那一刻**的实时快照，此时状态已翻转，
于是出现「`WIFI_CONNECT` 显示已断开」这种自相矛盾的记录；「SSID 被系统抹除」也是错误时机的读数。

修法：详情文案按**事件类型**写（快照状态只作为括号里的附加信息）；**心跳里带上当前 SSID**
（`当前WiFi=xxx` / `(抹除)` / `未连接` + 定位总开关状态），这样后台可读性每 5 分钟有一条干净证据。

### v0.1.2-m0 复测要看的四点

1. ② 页「看门狗精确闹钟」应显示**已授权** —— v0.1.3 起改用 `USE_EXACT_ALARM`，
   Android 13+ **安装即自动授予，不需要任何手动操作**（v0.1.2 曾要求手动授权，
   结果在系统列表里根本找不到本应用，那个坑已修）
2. 锁屏挂 8 小时后：心跳最大间隔是否 ≤600s、心跳里 `当前WiFi=` 是不是真名
3. 日志里有没有 `看门狗：哨兵不在运行…已自动拉起` 这条 —— 出现即说明**自愈真的生效了**
4. 重启手机后：日志顶部应有 `BOOT` + `SERVICE_START`（这一项 v0.1.1 已通过，回归确认即可）

### 复测前的前置条件（不做的话结论无效）

1. HyperOS：**自启动**开 + **省电策略→无限制** + 任务卡片里把「如约」**下拉锁定**
2. 确认 ② 页点的是「启动哨兵」（不是停在旧状态）
3. 挂机期间**不要**点「强行停止」，**不要**卸载重装（覆盖安装才保留数据）
4. 先截保活结论 → **再**重启手机 → 另截一张验证开机自启（两件事分开做，
   否则心跳断档分不清是"被杀"还是"你重启的"）

## ② 复测结论（v0.1.3，2026-10-09）→ ✅ **通过**

用户已确认：**HyperOS 三项设置全开**、**测试时未插电**。8 小时挂机结果：

| 观察 | 数值 | 判读 |
|---|---|---|
| 心跳连续性 | 50 条，跨越 10 小时，**零 `SERVICE_STOP`** | ✅ 服务全程**没被杀** |
| 心跳最大间隔 | 12238 秒（3.4 小时，出现在夜间） | ⚠️ **不是被杀** —— 无 STOP 记录，是**设备深度睡眠**把定时器推迟了 |
| 后台读 SSID | 每条心跳都带 `当前WiFi=TP-LINK_1602_5G` / `plqrd_5GHz` | ✅ **稳定可读**（比上轮"碰巧读到"可信得多） |
| 开机自启 | 重启后 ② 页自动变「运行中」、日志有 `BOOT` + `SERVICE_START` | ✅ |
| 看门狗精确闹钟 | ② 页显示「已授权」 | ✅ v0.1.3 的 `USE_EXACT_ALARM` 生效，**用户零操作** |

**关键判读经验（已写进统计页逻辑）**：心跳断档 ≠ 服务被杀。只有出现 `SERVICE_STOP`
且之后没有 `SERVICE_START` 才算被杀；没有 STOP 的长间隔是设备深度睡眠，
属正常现象。这两者的修法完全不同，不能混着说。

**仍然待验的那一个风险**：深度睡眠期间发生的 WiFi 连接事件，`NetworkCallback` 能不能
被**及时**投递（心跳延迟是定时器行为，与事件投递不是一回事）。这只能在 M1 做
「到家提醒」端到端实测才能回答 —— 见 `docs/M1-验收.md`。

## 排障速查

| 现象 | 先查 |
|---|---|
| 到点没响 | HyperOS 自启动 / 省电策略 / 有没有被强行停止 / 日志里有没有 `ALARM_FIRED` |
| 锁屏不弹窗只有通知 | 全屏通知开关 / 后台弹出界面 |
| 到家不提醒 | WiFi 权限 / 哨兵是否在跑 / 日志里有没有 `WIFI_CONNECT` |
| 提醒重复响 | 冷却规则没生效（看 `⑤` 的连断次数） |
| 重启后全失效 | 日志有没有 `BOOT`；有则查 FGS 启动被拒，没有则查自启动权限 |
