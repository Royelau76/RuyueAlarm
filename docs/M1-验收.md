# M1 验收：到家提醒的端到端实测

## 要回答的问题

M0 只证明了「服务活着、能读到 SSID、闹钟能全屏弹出」这三件事。
但**还有最后一环没验**：

> 深度睡眠期间发生的 WiFi 连接事件，`NetworkCallback` 会不会被**及时**投递？

为什么值得单独验：M0 复测里心跳最大间隔到过 3.4 小时 —— 那是**定时器**被 Doze 推迟，
跟**网络事件投递**不是一回事。如果事件也会被压到下一个维护窗口才处理，
那"到家提醒"就可能延迟几十分钟，产品价值直接归零。

**这一项拿真实场景测，没有别的办法。**

## 前置条件

1. 装上 v0.2.1-m1（覆盖安装，日志保留）
2. 检查权限（覆盖安装可能重置）：`NEARBY_WIFI_DEVICES` / `ACCESS_FINE_LOCATION` /
   `ACCESS_BACKGROUND_LOCATION` / 通知
3. HyperOS：自启动开、省电策略→无限制、任务卡片下拉锁定（用户已确认全部开启）
4. ② 页确认哨兵「运行中」

## 配置提醒

新建一条「到家提醒」：

| 字段 | 值 |
|---|---|
| 标题 | 到家提醒（测试） |
| 触发 | 只启用 **WiFi** |
| 目标 SSID | `plqrd_5GHz` **和** `plqrd` 都加上（一台路由器双频两个名字，只绑一个会漏） |
| 去抖 | **15 秒**（依据 M0 第 5 项：72 小时仅连断 2~3 次） |
| 冷却 | 一天（测试时如果要连测，先改成 1 分钟，测完改回来） |

保存后哨兵会自动保持运行。

## 测试 A：亮屏（先排除低级错误）

1. 关闭手机 WiFi
2. 等 1 分钟
3. 打开 WiFi，保持亮屏
4. 记录：**从 WiFi 连上到响铃，隔了几秒**
5. 日志里应看到：`WIFI_CONNECT` → （15 秒后）`ALARM_FIRED` → `RING_OPENED`

**期望**：连上后 15~20 秒内响。

## 测试 B：锁屏放置（关键场景）

1. 关闭 WiFi
2. **按电源键锁屏，静置 1 小时以上**（别碰手机）
3. 打开 WiFi（如果关屏后无法操作，就改成：先开着 WiFi 出门，回家路上手机一直在锁屏口袋里）
4. 记录：**进家门到响铃的实际延迟**
5. 看日志里 `WIFI_CONNECT` 与 `ALARM_FIRED` 的时间戳差

**期望**：差值接近 15 秒（去抖）+ 事件投递延迟。
**若差值达到分钟级甚至更久** → 说明事件投递也被 Doze/冻结推迟了，需要加固：
- 优先确认 HyperOS 白名单与 Doze 白名单（`adb shell dumpsys deviceidle whitelist +com.ruyue.alarm`）
- 还不行就在 M2 里加"到达后补触发"：即使延迟，也要在唤醒后立刻补一次判定

## 判读

| 结果 | 结论 |
|---|---|
| A、B 都在 1 分钟内 | ✅ M1 的 WiFi 触发可用，可以开始日常使用 |
| A 正常、B 延迟大（分钟级） | ⚠️ 事件投递被系统推迟 → 先查白名单，再考虑 M2 加"唤醒后补判定" |
| A、B 都不触发 | ❌ 先看日志有没有 `WIFI_CONNECT`：没有则是 WiFi 权限/网络回调问题；有但没 `ALARM_FIRED`，则是触发引擎或 SSID 匹配问题 |

## 排查用速查

```powershell
# 服务是否活着 / 有没有被白名单
adb shell dumpsys deviceidle whitelist | findstr ruyue
# 看最近的日志事件（也可以用 App 里的「全部日志」页）
adb logcat -d | findstr /I "ruyue"
```
